# 学段衔接审计报告（2026-08-30）

> 目的：核查 6-8 → 9-12 的能力过渡是否平滑，判断是否需要桥接项目。
> 方法：不用体感判断，直接扫描两个学段**所有项目的 `defaultXml`**，统计积木的真实使用频次，
> 用「9-12 用到、但 6-8 零接触的积木」来定位孩子会**冷启动**的概念。

## 一、结论速览

| 维度 | 6-8 铺垫 | 9-12 用量 | 判定 |
|------|---------|----------|------|
| **变量** | set_var 7 / change_var 5 / get_var 11 | 38 / 27 / 37 | ✅ **平滑**（有基础，只是加量） |
| **函数** | **0**（零接触） | func_def 9 / func_call 14 | ⚠️ **冷启动，但属合理 i+1**（见下） |
| **列表** | **0**（零接触） | 共 96（list_add 单块 61） | ✅ **可接受**（9-12 第 7 个分类，前隔 6 类有缓冲） |
| **键盘** | **1**（仅 `key_forward`） | 42 | ⚠️ **中等断层** |
| **写代码** | 积木 | **仍是积木**（9-12 全 77 项无代码模式） | ❗**前提需修正**：这一步不在 6-8→9-12 |

**总判定：6-8 → 9-12 基本平滑，不需要新增桥接项目。**
真正需要处理的断层在 **9-12 → 13-16**（见第四节），本轮已做对应修复。

### 为什么「函数」虽是冷启动、却判定为可接受

9-12 的**第一个**分类就是 A·函数，第一关 `fn_square`（用函数画正方形）看起来很陡。但拆开看：

- 函数体内是 `落笔 → 重复 4 次（移动 100 / 右转 90）→ 抬笔`
- 这三样在 6-8 分别被用过 **41 / 59 / 39 次**，是孩子最熟练的动作

也就是说新增概念**只有「打包 + 调用」这一个**（i+1），其余全是旧知。
加上 `erLingHint` 给出了明确的三步引导，判定为**合理的教学设计，无需桥接**。

### 变量为何判定为平滑

6-8 的数学分类已系统性铺垫变量：`count10`、`count_apples`、`multiplication`、`calculator`、
`compare_size`、`odd_even`，加上本轮新增的 PBL 作品 `step_counter`。
9-12 只是把用量放大（set_var 7→38），**概念上是延续而非新授**。

## 三、本轮发现并修复的两个真问题

### 问题 1：9-12「代码初探」名不副实（已修）

- `stages.ts` 里 9-12 名为「代码初探」，tagline 写着「从积木过渡到 JavaScript」；
  但实测 **9-12 全部 77 个项目 `codeMode: 0`**，全是积木、没有一行 JS。
- 更关键：学习页的代码预览块原先是 `className="hidden"`（仅调试用），
  即**孩子学完 77 个项目，全程看不到自己搭的积木对应什么代码**。
- **修复**：改为按 `stage.id === "stage-9-12"` 显示「生成的 JavaScript」预览区。
  这样「代码初探」才真正成立，也为 13-16 手写 JS 做了铺垫。6-8 保持隐藏（纯积木，避免干扰）。

### 问题 2：工具箱过滤的作用域被文档含糊带过，是个埋雷（已补警示）

- `plan-track.md` 记载「6-8 岁 · 纯积木：工具箱过滤为 `[...]`（不含变量/函数）」。
  这条**只对造物工坊 `/studio` 成立**（`STAGE6_CATEGORIES` 仅由 `StudioClient` 传入）。
- **学习页 `/learn/[id]` 不传 `toolboxCategories`，用的是全量 `TOOLBOX`（63 块）**。
- 危险在于：6-8 的数学与综合项目**实际依赖变量积木**
  （`count10`/`count_apples`/`multiplication`/`calculator`/`compare_size`/`odd_even`/`step_counter`）。
  若有人照文档把「不含变量」当成全局规则去"修正"学习页，这些项目的**自己做环节会直接不可完成**，
  而且**示范仍能正常跑**（`defaultXml` 不受工具箱影响）——迷惑性极强、极难排查。
- **修复**：在 `plan-track.md` 5.3 节写明作用域，并标注这条禁令。

### 问题 3：首页宣称 13-16 学 Python，实际全是 JavaScript（已修）

- `app/page.tsx` 的 13-16 卡片描述原文是「用 **Python** 和网页技术做完整的独立项目」。
- 但全站 **53 个 13-16 项目 100% 是 JavaScript**（`codeMode: 53` / `defaultCode: 53`），
  **代码库里不存在任何 Python 内容**（全局搜索 `Python` 仅命中该行文案与一处竞品对标描述）。
- 这是**对家长最致命的一类文案错误**：会直接招来想学 Python 的用户、或让想学 JS 的用户以为没有。
- **修复**：改为「离开积木、手写 JavaScript：做工具、模拟、算法与创意作品。」，
  并同步把 9-12 卡片描述改为与 `stages.ts` 一致的准确表述。

## 四、真正的断层在 9-12 → 13-16（本轮未解决，建议排期）

```
stage-6-8  ：111 项，codeMode   0，defaultXml 110   ← 积木
stage-9-12 ： 77 项，codeMode   0，defaultXml  77   ← 积木（无任何代码）
stage-13-16： 53 项，codeMode  53，defaultCode 53   ← 手写 JavaScript
```

孩子要连做 **188 个积木项目**，然后突然被要求手写
`for (let i = 0; i < 4; i++) { __runtime.move(100); __runtime.turn(90); }`——这是断崖式跨越。

13-16 第一关 `js_square` 的 `missionBrief` 已经解释了 `__runtime` 是什么，
算是温和引入，但「从拖到写」的跨度仍然很大。

**建议（下一轮，按性价比排序）**：

1. **9-12 后期加 1–2 个「读代码」项目**：给出一段 JS 让孩子预测结果 / 找出错误。
   只要求读不要求写，是把「看代码」（本轮刚打通）推进到「写代码」的最低台阶。
2. **13-16 首分类 K·js 前加 1 个「积木 ↔ 代码对照」过渡关**：
   左栏积木、右栏对应 JS，让孩子看到一一映射关系，消除"代码是天书"的恐惧。
3. 9-12 的 D·键盘分类：6-8 只铺垫了 1 个项目（`key_forward`）却要承接 8 个键盘项目，
   可考虑在 6-8 的 PBL 补一个键盘综合作品——但优先级低于上面两项。
